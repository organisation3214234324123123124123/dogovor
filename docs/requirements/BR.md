# Бизнес-правила (BR)

Источник: SRS v3, раздел «Бизнес-правила». Текст скопирован без изменений по смыслу.
Правила проверяются на сервере; интерфейс только подсказывает. Нарушение даёт 422 или 409 с кодом из [api.md](api.md).

| ID | Правило | Где применяется |
| --- | --- | --- |
| BR-1 | Исполнителем может быть только участник серии. Нового человека ведущий сначала добавляет в состав — прямо из панели | FR-05, FR-13, FR-43 |
| BR-2 | Срок — дата не раньше сегодняшней по поясу серии. Если дату не удалось извлечь, исходная фраза хранится в due_text и даёт пробел due_vague | FR-11, FR-13, FR-20 |
| BR-3 | «Согласовано на встрече» ставится, только если исполнитель присутствует, есть due_date и нет открытых пробелов no_assignee, no_due, due_vague, due_past. Пробел vague_action не блокирует — решает ведущий | FR-25 |
| BR-4 | Пункт без исполнителя при рассылке идёт в итог с пометкой «не назначен», получает статус pending без ссылки и первым попадает в сверку следующей встречи | FR-28, FR-42 |
| BR-5 | Рассылка идемпотентна: повторное нажатие не создаёт новых писем (dedupe_key = meeting_id:type:recipient). Пункт, добавленный после рассылки, уходит отдельным CONFIRM_REQUEST. Форматы ключей — ниже, «dedupe_key (BR-5)» | FR-28, FR-30 |
| BR-6 | Новый срок от исполнителя — не раньше сегодняшнего дня по поясу серии и не позже исходного срока + 60 дней. Смена срока исполнителем считается принятием пункта; ведущий получает HOST_RESPONSE и видит смену в сверке. Подтверждать новый срок ведущему не нужно; если не согласен — переносит или переназначает пункт (решение 23.10) | FR-31, FR-34 |
| BR-7 | Рабочие дни — понедельник–пятница по поясу серии. Функция add_business_days(date, n); производственный календарь РФ подключается позже без смены её интерфейса | FR-33, FR-40, FR-42 |
| BR-8 | DUE_TOMORROW создаётся при рассылке пункта со сроком, перепланируется при смене срока и отменяется при done и cancelled. Если до срока меньше одного рабочего дня, напоминание не создаётся | FR-40 |
| BR-9 | Загрузка исполнителя — число его пунктов в pending и accepted во всех сериях ведущего со сроком в ближайшие 7 дней. Предупреждение — при 5 и больше; порог меняется в настройках серии | FR-26 (Should) |
| BR-10 | CONFIRM_REPEAT уходит один раз через 1 рабочий день после первого письма, если хотя бы один пункт получателя по этой встрече всё ещё в pending. То же после «Переназначить»: новому исполнителю один повтор на одно переназначение, через 1 рабочий день от него; не создаётся, если у него по этой встрече уже стоит неотправленный CONFIRM_REPEAT (пункт попадёт в это письмо) | FR-33, FR-43 |
| BR-11 | Не больше 3 писем одному человеку в неделю от одной серии (кроме HOST_RESPONSE ведущему). Лишние объединяются в одно письмо на следующий рабочий день | все письма |
| BR-12 | GET по ссылке никогда не меняет состояние: почтовые сканеры открывают ссылки сами. Кнопка в письме ведёт на страницу, действие подтверждается POST | FR-32 |
| BR-13 | (этап 3) Режим со звуком стартует только после отметки ведущего «Участники предупреждены»; отметка пишется в журнал. Ведущий выключает распознавание в любой момент | FR-60, вне MVP |
| BR-14 | Звук не сохраняется нигде. Текст расшифровки живёт только в памяти сервисов до рассылки итога, но не дольше 4 часов. В базу попадают только поля пунктов | этап 3 |
| BR-15 | LLM заполняет только пустые поля и никогда не трогает поля из items.manual_fields — их правил ведущий | FR-12, FR-21 |
| BR-16 | Письма одного типа одному получателю в одном запуске воркера уходят одним письмом. В момент отправки условие проверяется снова: закрытый пункт письма не получает | все письма, FR-16 |
| BR-17 | Временная ошибка почты (4xx, таймаут) — до 3 повторов через 5, 15 и 60 минут; постоянная (5xx) — failed сразу | отправка писем |
| BR-18 | Ссылка действует до большего из двух сроков: выдача + 14 дней или позднейший срок открытых пунктов получателя по этой встрече + 30 дней. Пересчитывается при смене срока | FR-30, FR-31 |
| BR-19 | Журнал item_events только на вставку. В data пишутся только id, статусы и даты — без текста пунктов, имён и комментариев. Свободный текст (комментарий к «Это не моё») хранится в item_comments: его можно чистить и обезличивать, не трогая журнал | FR-31, FR-45, FR-52 |
| BR-20 | Сроки хранения: пункты, комментарии и участники — пока серия активна и 1 год после архивации; ссылки — удаляются через 30 дней после истечения; payload писем — 90 дней; item_events и llm_calls — 1 год, удаляет отдельная служебная роль БД; аналитика без ПДн — 2 года; бэкапы — 14 дней. Чистку запускает ежедневная задача Celery Beat | ежедневная задача (своего FR нет) |
| BR-21 | Во внешнюю LLM уходят строка решения, дата и участники в виде id и имени без фамилии. Логирование запросов на стороне провайдера отключается, если провайдер это позволяет. С провайдером заключается договор поручения обработки ПДн | FR-12, FR-21 |

## dedupe_key (BR-5)
`notifications.dedupe_key` UNIQUE: вставка с тем же ключом не создаёт письма (`ON CONFLICT DO NOTHING`).
Ключ без различителя годится только для письма, которое по смыслу бывает один раз. Если письмо законно повторяется
(тот же исполнитель снова получает пункт после переназначения A → B → A, срок вернули на прежнюю дату, второй сброс пароля),
в ключ входит различитель: версия пункта `items.version` на момент события или id события. В SRS у трёх типов его нет — OQ-16.

| Тип | dedupe_key | Почему так |
| --- | --- | --- |
| SUMMARY | `{meeting_id}:SUMMARY:{person_id}` | Один итог на встречу; повторное «Разослать» из `sent` его не шлёт (OQ-02) |
| CONFIRM_REQUEST | `{item_id}:CONFIRM_REQUEST:{person_id}:{version}` | Повтор после переназначения обратно; повторное «Разослать» версию не меняет — письма нет |
| CONFIRM_REPEAT | `{meeting_id}:CONFIRM_REPEAT:{person_id}` | Один раз (BR-10) |
| CONFIRM_REPEAT после переназначения | `{meeting_id}:CONFIRM_REPEAT:{person_id}:R{item_id}.{version}` | Свой ключ на каждое переназначение, чтобы не упереться в уже занятый ключ встречи (BR-10) |
| HOST_RESPONSE | `{item_id}:HOST_RESPONSE:{item_event_id}` | Каждый ответ исполнителя — своё событие журнала |
| DUE_TOMORROW | `{item_id}:DUE_TOMORROW:{due_date}:{version}` | Срок перенесли и вернули: старое письмо отменено, нужно новое |
| ITEM_CHANGED | `{item_id}:ITEM_CHANGED:{version}` | Как в SRS; несколько правок объединяет BR-16 |
| ITEM_REASSIGNED | `{item_id}:ITEM_REASSIGNED:{person_id}:{version}` | Повтор при A → B → A → B |
| PASSWORD_RESET | `{user_id}:PASSWORD_RESET:{reset_id}` | Каждый запрос сброса — новый `reset_id` (uuid); лимит запросов — FR-03 |

`{version}` — версия пункта после изменения, которое породило письмо; id и даты — как в базе (uuid, `YYYY-MM-DD`).
