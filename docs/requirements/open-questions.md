# Открытые вопросы по требованиям

Противоречия и дыры, найденные при нарезке SRS v3 (23.10): здесь только то, чего в SRS нет или что в нём расходится.
У каждого вопроса предложено решение. Если решение поменяется, меняем FR отдельным коммитом.

Часть вопросов уже поднята у аналитиков: флаг `is_active` у промпта, тип пробела «нет критерия готовности», правки «API-контракта», «Сделано» в SUMMARY, enum `notifications`. Для каждого ниже дано рабочее решение.

## OQ-01. `GET /p/{token}` описан как HTML
В полном SRS: «Страница по ссылке (HTML)». Но фронтенд — одно React SPA, /p — его отдельный бандл.
**Решение:** страница — это фронтенд (отдельное приложение, в этот репозиторий не входит), API `GET /api/v1/p/{token}` возвращает JSON. Заголовки `Referrer-Policy` и `X-Robots-Tag` — на обоих ответах.

## OQ-02. Как пункт, добавленный после рассылки, выходит из draft
BR-5: «пункт, добавленный после рассылки, уходит отдельным CONFIRM_REQUEST». Но draft → pending бывает только по «Разослать», а встреча уже `sent`.
**Решение:** во встречу в `sent` можно добавлять пункты (draft). Повторное «Разослать» отправляет только новые draft-пункты: pending/accepted по обычным правилам, CONFIRM_REQUEST новым исполнителям; SUMMARY повторно не уходит (dedupe).

## OQ-03. Подтверждение «Осталось N пробелов» в API и код ALREADY_SENT
FR-28 требует подтверждения, но ручка `POST /meetings/{id}/send` его не описывает. Где используется `ALREADY_SENT` — не сказано.
**Решение:** тело `{"confirm_open_gaps": bool}`; есть открытые пробелы и false → 422 `GAPS_OPEN` с числом в `errors`; true → рассылка. Повторный send без новых пунктов → 200 без новых писем (BR-5). `ALREADY_SENT` — для `closure` и `accept-in-meeting` у встречи в `sent`.

## OQ-04. Два письма при рассылке и «Сделано» в SUMMARY
Исполнитель pending-пункта при рассылке получает SUMMARY (со ссылкой и кнопками) и CONFIRM_REQUEST — два письма с одним смыслом, оба идут в лимит BR-11 (3 в неделю). В полном SRS в таблице писем CONFIRM_REQUEST — только «новому исполнителю после рассылки», а в таблице переходов и FR-30 — и при рассылке. Также в SUMMARY у принятого пункта нет «Сделано», а на странице (FR-31) есть. Формат dedupe_key в BR-5 (`meeting_id:type:recipient`) расходится с ключами по типам.
**Решение:** делаем как в FR-30 и таблице переходов (оба письма); страница — по FR-31, письмо — по таблице писем; dedupe_key — по таблице писем. Вопрос про двойное письмо отправить аналитикам.

## OQ-05. Жизненный цикл встречи
Статусы planned, live, closing, sent, но переходы не описаны. «Начать встречу» создаёт встречу «сейчас», откуда `planned` — неясно (только для повестки «до встречи», FR-08). Код для второй встречи в live/closing не задан.
**Решение:** `POST /series/{id}/meetings` создаёт встречу сразу в `live`; `planned` пока не используется (Should FR-08 — повестка во время встречи). live → closing (FR-22), closing → live («Ещё 5 минут», FR-23), closing → sent (FR-28). Вторая активная встреча → 409 `MEETING_ALREADY_LIVE`.

## OQ-06. Коды ошибок для случаев, которых нет в таблице
**Решение** (коды — по таблице в [api.md](api.md)): занятый e-mail при регистрации → 409 `EMAIL_TAKEN`; блокировка входа (FR-02) → 429 `RATE_LIMITED` + Retry-After; истёкшая или использованная ссылка сброса пароля → 410 `LINK_EXPIRED`; нет или неверен CSRF → 403 `CSRF_INVALID`; смена исполнителя через PATCH после рассылки → 422 `USE_REASSIGN`; отсутствующий исполнитель или нет due_date при «Согласовано» → 422 `GAPS_OPEN`; новый срок исполнителя больше +60 дней → 422 `DUE_TOO_LATE`; нет `If-Match` → 428 `PRECONDITION_REQUIRED`; несовпадение версии → 409 `VERSION_CONFLICT`; «Скопировать итог» у встречи в `live` → 409 `SUMMARY_NOT_READY`; `/admin` без токена → 403 `ADMIN_FORBIDDEN`, с пустым `ADMIN_TOKEN` → 403 `ADMIN_DISABLED`; повторный dismiss → 200 без нового события.

## OQ-07. Ручек нет в списке API
Нет ручек для: стороны участника (organizations), пропуска сверки (`review_skipped`), текста «Скопировать итог» (`summary_copied`), новой версии промпта, удаления пункта в WS, догрузки после обрыва; не описан «служебный доступ» для `/admin`. Ручки повестки есть только в полном SRS.
**Решение:** сторона — поле `organization` (название) в `POST /series/{id}/members`, организация ищется или создаётся; своя организация (`is_own`) создаётся при регистрации. `POST /meetings/{id}/review/skip`; `GET /meetings/{id}/review`; `POST /meetings/{id}/summary-text` (возвращает текст и пишет событие); `GET, POST /admin/llm/prompts`; WS-событие `item.deleted`; догрузка — `GET /meetings/{id}` со всеми пунктами и версиями. Служебный доступ — отдельная схема безопасности: заголовок `X-Admin-Token`, сравнивается с переменной окружения `ADMIN_TOKEN` за постоянное время; пустая переменная — `/admin` выключен (403 `ADMIN_DISABLED`); сессия ведущего (cookie или bearer) для `/admin` не действует. Повестка — ручки из полного SRS.

## OQ-08. Разбор правилами: недоописанные случаи
Что пишется в `what` на этапе 1 (правила извлекают только «кто» и «срок»); «к 20.10», если дата уже прошла; «до пятницы», сказанное в пятницу; два участника с одним именем; подстановка «{Имя}» в вопросе `no_due`, когда исполнителя нет. FR-13 говорит «исполнитель из состава встречи», BR-1 — «участник серии».
**Решение:** `what` = raw_text без распознанных имени и срока; «к 20.10» в прошлом → дата текущего года и пробел `due_past`; «до пятницы» в пятницу → сегодня; дата без года, прошедшая больше чем полгода назад (30.12 и «к 05.01»), → следующий год; тёзки → исполнитель пуст (`no_assignee`); без исполнителя вопрос «К какому числу?». Исполнитель — по BR-1 (участник серии).

## OQ-09. Один вопрос на пункт или на каждый пробел; нет пробела «нет критерия готовности»
AC-1.1: у пункта «один готовый вопрос»; FR-21: «к каждому пробелу — готовый вопрос». Контракт LLM возвращает один `question`. Если словарь нашёл `vague_action`, а LLM сказала `false` — неясно, кто прав. Тип «нет критерия готовности» не добавлен (вопрос у аналитиков).
**Решение:** вопрос хранится у каждого пробела; панель показывает один на пункт: вопрос LLM, иначе первый по порядку no_assignee, no_due, due_vague, due_past, vague_action. Пробел по словарю LLM не закрывает (LLM только дополняет). Пятого типа нет, делаем пять типов.

## OQ-10. «Согласовано на встрече»: снятие и сброс
Не сказано, можно ли снять отметку и что с ней при смене исполнителя или срока до рассылки.
**Решение:** снятие — повторный вызов с `{"value": false}`; смена исполнителя сбрасывает отметку; смена даты оставляет её, если BR-3 по-прежнему выполняется (AC-2.4).

## OQ-11. Чего не хватает в модели данных
- Порог загрузки BR-9 «в настройках серии» — поля нет → `series.load_warning_threshold int null` (NULL — порог по умолчанию 5; миграция 0003).
- Enum `notifications.type` без ITEM_CHANGED, ITEM_REASSIGNED → добавить; письмо сброса пароля (FR-03) → тип `PASSWORD_RESET` с `recipient_user_id` (миграция 0003).
- Токен сброса пароля и счётчики неудачных входов (FR-02, FR-03) хранить негде → таблицы `login_attempts` и `password_reset_tokens` в БД (срок токена 1 час, окно блокировки 15 минут), токен гасится при использовании.
- Согласие ведущего на обработку ПДн (NFR-12) → `users.pd_consent_at timestamptz null`, ставит регистрация (миграция 0003).
- `llm_prompts.is_active` или «последняя по номеру» → флаг `is_active` (позиция команды: откат одним переключением).


## OQ-12. Кто получает SUMMARY
«Всем участникам встречи»: включая отсутствующих? Исполнитель, добавленный в состав серии из панели, может не быть в `meeting_participants`.
**Решение:** все `meeting_participants` (и присутствующие, и нет; отсутствующим итог нужнее всего); человек, добавленный в серию во время встречи, сразу добавляется в участники встречи.

## OQ-13. Время: граничные случаи
«До срока меньше одного рабочего дня» (BR-8); от чего считать «pending старше 2 рабочих дней» (FR-42); где проверять 60 решений в минуту (NFR-10).
**Решение:** напоминание не создаётся, если его время (09:00 предыдущего рабочего дня) уже прошло; 2 рабочих дня считаются от `sent_at`; лимит 60/мин — в приложении (nginx не знает meeting_id).

## OQ-14. Страница по ссылке: детали
Кнопки для `disputed` и `done` не описаны; GET пишет `link_opened` и `last_used_at` — это запись, хотя BR-12 «GET ничего не меняет»; откуда брать `notification_type` для `link_opened`.
**Решение:** disputed и done — показываются со статусом, без кнопок; запись `link_opened` и `last_used_at` разрешена (статус пунктов не меняется); тип письма — параметр `?n=<TYPE>` в ссылке.

## OQ-15. Мелочи
- FR-23: в дополнениях к SRS «вне объёма MVP», в SRS v3 — Should, этап 2 → берём v3. Таймер на фронтенде, он вызывает `POST /closure` с `trigger = timer`.
- `capture_mode = audio` на этапах 1–2 → 422 `VALIDATION_ERROR` до этапа 3.
- FR-44: показывать ли draft → нет, только разосланные.
- FR-52: «Участник N» — порядковый номер обезличенных у ведущего; повторный вызов → 200 без изменений; письма в `queued` этому человеку → `cancelled`.


## OQ-16. dedupe_key: письма, которые законно повторяются
SRS: `dedupe_key` UNIQUE и форматы `item:CONFIRM_REQUEST:person`, `item:ITEM_REASSIGNED:person`, `item:DUE_TOMORROW:due_date`. При переназначении A → B → A второй CONFIRM_REQUEST для A и второй ITEM_REASSIGNED для B получат тот же ключ и не уйдут; так же DUE_TOMORROW, если срок перенесли и вернули. Ключа для PASSWORD_RESET в SRS нет.
**Решение:** UNIQUE оставляем; в ключи этих типов добавляем различитель — версию пункта (`{version}`) или id запроса сброса. Форматы — [BR.md](BR.md#dedupe_key-br-5). Нужно подтверждение аналитиков (А-4).

## OQ-17. DELETE в журнале item_events
SRS: «у роли приложения нет прав UPDATE и DELETE; по сроку удаляет служебная роль». Но FR-15 физически удаляет draft-пункт, а `item_events.item_id` — `ON DELETE CASCADE`.
**Решение:** UPDATE запрещён триггером всегда. Прямой DELETE тоже запрещён триггером (миграция 0003); строки журнала уходят только каскадом вместе с пунктом: удаление draft (FR-15; сервис удаляет только draft) и чистка BR-20 через удаление пунктов. Журнал по сроку чистит задача BR-20 без отдельной роли: миграция 0006 разрешает прямой DELETE при `app.retention_cleanup = on` (ставит только задача). Вопрос передан аналитикам (А-5).

## OQ-18. Размытость и вопрос одним вызовом parse
FR-21 AC7 предполагает отдельные вызовы (`gaps`, `question`). Один вызов `parse` возвращает и разбор, и `vague_action` с `question`: меньше задержка и затрат, один промпт.
**Решение:** вызовы `gaps`/`question` не делаем, в `llm_calls` пишется task = `parse`.

## Вопросы аналитикам
Неоднозначности SRS v3, на которые нужен ответ аналитиков. До ответа работаем по указанному решению.

- **А-1. «Перенести» из disputed.** Таблица переходов разрешает «Перенести» только из pending и accepted, а правку срока по FR-16 — из pending, accepted и disputed. В коде: `actions/reschedule` из disputed → 409 `INVALID_TRANSITION`, `PATCH /items/{id}` со сроком у disputed — проходит (FR-16). Нужно ли одно правило?
- **А-2. Этап FR-09.** Архивирование серии и исключение участника — Should; в списке Should этапа 2 их нет, а этап 1 включает «серии». В коде: этап 2.
- **А-3. FR-51: метрики в CSV или события.** Требование: «выгрузка событий и расчёт метрик PRD в CSV», а ручка одна — `GET /admin/export/events.csv`. Считает ли метрики сервис (отдельная выгрузка) или команда из events.csv? В коде: только events.csv, метрики — по формулам из FR-51 вне сервиса.
- **А-4. dedupe_key без различителя** (OQ-16): форматы SRS теряют законные повторные письма.
- **А-5. Удаление из журнала** (OQ-17): «только INSERT» против физического удаления draft-пункта (FR-15).
