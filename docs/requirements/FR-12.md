# FR-12. Разбор строки нейросетью (LLM)

Приоритет: **Must** · Этап: **2** · Модуль: панель встречи

## Требование (SRS v3)
Разбор LLM: «что», «кто», «срок», «готово» из строки. Заполняет только пустые поля и не перезаписывает правки ведущего.

## Критерии приёмки
1. Вход в LLM: `{"text", "today", "weekday", "participants": [{"id", "name"}]}`; name — имя без фамилии (BR-21). Ничего другого (прошлые пункты, e-mail) не уходит.
2. LLM вернула валидный ответ → заполняются только пустые поля пункта; уже заполненные правилами не меняются.
3. Поле из `items.manual_fields` не меняется никогда (BR-15).
4. `assignee_id` не из `participants` → поле отброшено.
5. `due_date` невалидна или раньше `today` → поле отброшено.
6. `what` не начинается с глагола в инфинитиве → поле отброшено.
7. `question` длиннее 120 символов → поле отброшено.
8. Невалидный JSON → один повтор; второй невалидный → `llm_calls.outcome = invalid_output`, пункт остаётся с разбором по правилам.
9. Нет ответа за 8 с → `outcome = timeout`, панель работает на правилах (NFR-02, AC-1.8).
10. Каждый вызов пишет `llm_calls`: meeting_id, task, provider, model, prompt_id, latency_ms, input_tokens, output_tokens, outcome, created_at; текста запроса и ответа нет. В `analytics_events` вызов не пишется.
11. Промпт берётся из `llm_prompts` (активная версия задачи `parse`).
12. Текст запроса к LLM не пишется в логи (NFR-13).

## Правила и данные
- Адаптер `LLMClient`, OpenAI-совместимый интерфейс; смена провайдера — смена `base_url` и `model`. Температура 0, вывод по JSON-схеме.
- Выход: `what`, `assignee_id`, `due_date`, `due_text`, `done_criteria`, `vague_action`, `question`.
- **BR-15.** LLM заполняет только пустые поля и никогда не трогает поля из items.manual_fields — их правил ведущий.
- `is_active` или «последняя по номеру» — OQ-11.
