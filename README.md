# Договорились — сервис контроля исполнения решений встреч

Сервис позволяет:
- фиксировать решения регулярных встреч в виде пунктов: задача, ответственный, срок и критерий готовности;
- распознавать исполнителя и срок в свободном тексте пункта (правила разбора и YandexGPT);
- находить незаполненные поля в пунктах, например отсутствие срока или ответственного;
- вести встречу в реальном времени: изменения пунктов приходят участникам по WebSocket;
- рассылать итоги встречи, собирать подтверждения исполнителей и напоминать о сроках.

Стек: Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16, Redis 7, Celery.

## Быстрый старт
Для запуска требуется Docker с Docker Compose v2 (например, [Docker Desktop](https://www.docker.com/products/docker-desktop/)); демон Docker должен быть запущен.

```bash
git clone https://github.com/organisation3214234324123123124123/dogovor.git
cd dogovor
docker compose up
```

Команда запускает PostgreSQL, Redis, API и фоновые процессы Celery (worker и beat). Миграции базы данных применяются автоматически при старте API. Файл `.env` необязателен: без него используются значения по умолчанию.

`docker compose up` автоматически подключает `compose.override.yaml` и запускает сервис в режиме разработки: с демо-данными и служебным входом для Swagger.

### Проверка работоспособности
Выполните запрос к эндпоинту состояния:

```bash
curl http://localhost:8000/api/v1/health
```

Если сервис работает, ответ приходит с кодом `200` и полем `"status": "ok"`. Если база данных недоступна — с кодом `503` и `"status": "down"`.

### Документация API
Swagger UI доступен в браузере: http://localhost:8000/api/docs. Чтобы выполнять запросы от имени пользователя, нажмите **Authorize** и войдите под демо-учётной записью `host@example.com` / `demo1234`. Демо-данные и эта учётная запись доступны только в режиме разработки.

### Остановка и сброс
| Действие | Команда |
|---|---|
| Остановить сервис | `Ctrl+C` или `docker compose down` |
| Остановить и удалить данные базы | `docker compose down -v` |
| Запустить на другом порту, если 8000 занят | `BACKEND_PORT=8001 docker compose up` |

## Развёртывание на сервере
На сервере сервис запускается в боевом режиме: только с `compose.yaml`, без `compose.override.yaml`. В файле `.env` задайте `SECRET_KEY` длиной не менее 32 символов, а `DEV_MODE` и `DEMO_DATA` оставьте пустыми.

```bash
docker compose -f compose.yaml up -d
```

В боевом режиме демо-данные не загружаются, служебный вход `/auth/token` отключён, cookie сессии передаётся только по HTTPS. Сервис не запустится, если `SECRET_KEY` короче 32 символов или задан `ADMIN_TOKEN` короче 32 символов.

## Слои приложения
Каждый модуль разделён на три слоя: `router.py` → `service.py` → `repository.py`.
- **router** принимает HTTP-запрос, проверяет входные данные и формирует ответ;
- **service** содержит бизнес-правила (статусы пунктов, сроки, рассылки) и управляет транзакцией;
- **repository** выполняет запросы к базе данных.

Такое разделение предусмотрено SRS. Бизнес-правила не зависят от HTTP и базы данных, поэтому их проще покрывать тестами, а все запросы к БД собраны в одном месте. У модулей `gaps` и `notifications` нет собственных эндпоинтов, а у `live` — запросов к БД, поэтому соответствующих слоёв в них нет.

## CI/CD
При каждом push и pull request запускается `.github/workflows/ci.yml`:
- линтер и более 1100 тестов с минимальным покрытием кода 90%;
- проверка соответствия контракта API коду;
- применение миграций на пустой базе;
- поиск секретов в истории репозитория;
- запуск всего стека через `docker compose up` и сквозной сценарий ([tests/smoke/smoke.sh](tests/smoke/smoke.sh));
- проверка соответствия `db/schema.sql` миграциям.

После успешного прохождения CI в ветке `main` образ бэкенда публикуется в GitHub Container Registry (`release.yml`).

## Для разработчиков
Требуются [uv](https://docs.astral.sh/uv/), Docker и Make.

```bash
make install     # установка зависимостей
make test-db     # PostgreSQL и Redis для тестов
make check       # линтер, тесты, миграции, контракт API
make schema      # пересборка db/schema.sql после добавления миграции
make smoke       # сквозной сценарий на запущенном стеке
```

Локальные настройки: `cp .env.example .env`. Если не заданы `LLM_API_KEY` (YandexGPT) и `SMTP_HOST` (Yandex Postbox), используются заглушки: нейросеть возвращает заранее подготовленные ответы, а письма выводятся в лог.
