# База данных

PostgreSQL 16. Схема создаётся миграциями Alembic (`backend/migrations/versions/`) при старте контейнера `backend`.

| Файл | Что это |
|---|---|
| [schema.sql](schema.sql) | DDL всей схемы: 20 таблиц, перечисления (enum), индексы, ограничения, триггеры |
| [dump_schema.sh](dump_schema.sh) | Пересобирает `schema.sql` из миграций (нужен только Docker) |
| `backend/app/modules/*/models.py` | Модели SQLAlchemy, по модулю на каждую часть предметной области |
| `backend/migrations/versions/` | Миграции по порядку, от пустой базы |

Порядок работы: меняем модель → `make migration m="..."` → `bash db/dump_schema.sh` → в коммит идут модель, миграция и `schema.sql`. CI проверяет, что `schema.sql` совпадает с миграциями.

Стартовые данные (не схема): системный промпт разбора строки кладёт миграция `0005_llm_seed_prompts`, промпт покрытия повестки — `0007_agenda_matching_prompt`. Демо-данные (`backend/demo/*.yaml`) грузятся только при `DEMO_DATA=1`.

## Главные решения
- Ключи `uuid`; журналы `item_events` и `analytics_events` на `bigint` (растут быстро, нужен порядок).
- Время `timestamptz` в UTC; сроки пунктов `date` в поясе серии; e-mail `citext` (регистр не важен).
- Перечисления — enum PostgreSQL: неверное значение не попадёт в базу даже в обход API.
- Правила предметной области закреплены в базе, а не только в коде: одна идущая встреча на серию, одна действующая ссылка на пару человек–встреча, один открытый пробел каждого типа на пункт, одна активная версия промпта на задачу, уникальный `dedupe_key` письма (письмо не уйдёт дважды).
- Журнал пункта `item_events` только дописывается: UPDATE и прямой DELETE запрещены триггером.
- Удаление: у дочерних таблиц `CASCADE`; исполнитель пункта — `RESTRICT`; `analytics_events` и `llm_calls` переживают пункты (`SET NULL`).
- Персональные данные: `persons` не удаляются, а обезличиваются; текст разговора и звук не хранятся.

## Сверка с ERD аналитиков
ERD аналитиков: SRS, вкладка «SRS: Закрытие встречи», раздел «Модель данных» (таблица полей, ER-диаграмма в нотации crow's foot и её mermaid-код). В ERD 19 таблиц, из них 2 — на этап 4.

Сверка идёт с исходным ERD из SRS. `docs/requirements/data-model.md` — рабочая версия модели в репозитории: в ней отражены расхождения ниже.

**Совпадает:** 17 таблиц ERD есть в базе с теми же полями, типами и ключами: users, organizations, persons, series, series_members, meetings, meeting_participants, agenda_items, items, gaps, access_links, notifications, item_events, item_comments, analytics_events, llm_prompts, llm_calls.

**Расхождения и почему:**

| # | Что | В ERD | У нас | Почему |
|---|---|---|---|---|
| 1 | `tracker_connections`, `tracker_links` | есть | нет | Интеграция с трекерами — этап 4 по SRS; таблицы появятся вместе с ней |
| 2 | `login_attempts`, `password_reset_tokens` | нет | есть | FR-02: блокировка входа после 10 неудач (считаем и несуществующие адреса); FR-03: сброс пароля, в базе только SHA-256 токена, срок 1 час, одноразовый |
| 3 | `access_link_tokens` | нет | есть | FR-30 п.4: в каждом письме свой случайный токен; у одной ссылки исполнителя несколько действующих токенов, в базе только SHA-256 |
| 4 | `access_links.token_hash` | отпечаток токена из письма | отпечаток служебного токена, который никому не отправляется | Токены писем лежат в `access_link_tokens`; одна действующая ссылка на пару человек–встреча остаётся, как в SRS |
| 5 | `users.pd_consent_at`, `series.load_warning_threshold`, `series.archived_at` | нет | есть | NFR-12 (согласие на обработку ПДн); FR-26, BR-9 (порог предупреждения о нагрузке, пусто — 5; есть в контракте API); BR-20 (от даты архивации считаются сроки хранения) |
| 6 | `notifications.created_at`, `claimed_at`, `postponed`; статус `sending` | нет | есть | NFR-06 и BR-11: порядок отправки, защита от двойной отправки двумя обработчиками, отложенные из-за лимита 3 письма в неделю |
| 7 | `notifications.type`: `ITEM_CHANGED`, `ITEM_REASSIGNED`, `PASSWORD_RESET` | в таблице 5 типов | 8 типов | Первые два описаны в разделе SRS про письма, но не добавлены в таблицу; третий — для FR-03 |
| 8 | `llm_prompts.task`, `llm_calls.task`: значение `agenda`; `item_events.action` с 11 значениями; уникальный индекс открытых пробелов `gaps` (item_id, type) | нет / «enum» без значений / обычный индекс | есть | FR-27: запрос «покрытие повестки» пишется в журнал и имеет свой промпт; действия взяты из таблицы переходов статусов; не бывает двух открытых пробелов одного типа у пункта |
| 9 | `item_events`: защита журнала | отдельная служебная роль без прав UPDATE/DELETE | триггер; чистка по срокам снимает запрет флагом `app.retention_cleanup` | Временная замена: одна роль БД проще в docker compose; отдельная служебная роль, как в SRS, не реализована |
| 10 | `llm_prompts.created_by` | тип не задан | `uuid` (ведущий) | Администратор входит служебным ключом и пользователем не является; строка-метка, как в контракте API, не реализована |
| 11 | Доп. проверки и индексы | нет | есть | `meetings`: конец позже начала; `items`: `done_at` заполнен ровно при `done`; отпечатки ссылок ровно 32 байта; индексы по датам для ежедневной чистки (BR-20) |

Сжатая версия SRS (вкладка «SRS сжатый (1-2 этап)») по таблицам нейросети отличается от полной: там `llm_prompts` без `task` и `is_active`, `llm_calls` без `provider` и `prompt_id`. Схема сделана по полной версии; расхождение двух версий SRS — открытый вопрос к аналитикам.
